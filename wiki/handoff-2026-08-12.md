## What Was Done This Session

### Stub Cap Audit and Fix (Critical)

Examined all 6 Dafny stubs and 16 C# templates against their contracts. Found 4 categories of problems:

1. **Missing methods (7):** Dafny declared methods with no C# implementation — network-io sockets (OpenSocket, SocketSend, SocketRecv, CloseSocket), time-random (GetIsoTimestamp, RandomBool), console-io (ReadChar)
2. **Hollow methods (4):** database-io transactions were empty stubs with "simplified" comments — CloseConnection, BeginTransaction, CommitTransaction, RollbackTransaction
3. **No requires guards (systematic):** every stub ignored its Dafny preconditions
4. **Ensures violations (3):** ReadLine could return null, OpenConnection returned negative hash, ReadChar had type mismatch

All fixed. Real connection/transaction/socket pools. Requires guards on every method. 16/16 templates certified clean.

### The Bluejohn Discovery (Critical)

Examined T8 (CI/CD pipeline) — the meatiest trial. Found that the CLI is a hollow shell:

```csharp
case "start":
    Console.WriteLine($"Started workflow {workflowId}");
    break;
```

It prints a string. It doesn't call `PipelineEngine.RunPipeline()`. It doesn't call `DagResolver.Resolve()`. It doesn't call anything. All 8 Dafny modules are Z3-proven, all 10 C# files compile, but nothing is wired together. The program is a box of proven parts that don't talk to each other.

**Root cause:** The C# Implementation phase was redesigned to be purely mechanical (registry-driven stub caps, "no model generation"). The stub caps fill extern portals. But the wiring between components — the glue that connects the CLI to the pipeline engine to the DAG resolver to the scheduler — was never generated. The prompt asked for it ("wire I/O shells to call the translated Dafny methods") but the model was never called.

### `--test-assumptions Externs` Flag Discovered

Dafny can emit runtime contract checks for `{:extern}` methods. When enabled, the translated C# checks `requires` and `ensures` at runtime. If a stub violates the contract, it throws. ## The Big Picture

The proof methodology (wiki/proof-methodology.md) is:

```
1. SEED → Registry holds 17 proven panels
2. ASSEMBLE → Team picks panels, pipeline composes skeleton
3. TEST → Push data through CLI, push every GUI button, capture output
4. PROVE → Bot or human confirms it does what the spec said
5. CARVE → Pull working pieces back into the registry
```

We're at step 2 — the panels are assembled, the skeleton is composed, Z3 verifies it. But step 3 can't happen yet because the program doesn't run. The wiring is missing. The CLI is hollow. No data can flow.

## Key Decisions

1. **Option B: io-shell components get Dafny skeletons** — every component has a contract, not just Dafny components
2. **Wiring is deterministic** — orchestrator generates glue from dependency graph, no model call needed
3. **Stubs enforce requires at runtime** —ArgumentException on precondition violation
4. **Proof methodology: seed → assemble → test → prove → carve** — the registry grows from verified end products
5. **GUI testing is fully automatable** — every control is hotkey-reachable, no humans needed
6. **Dafny translates to 7 languages** — C#, Rust, JavaScript, Go, Java, Python, C++ — one proof, portable deployment
7. **`--test-assumptions Externs`** — Dafny can emit runtime contract checks for extern methods across all target languages

## Lessons Learned

1. **"Green" means the pipeline ran, not the program works** — Z3 green + compile green ≠ functional program. The wiring gap proved this.
2. **Stubs are the seam** — Z3 assumes the C# stub satisfies the contract. Without requires guards, the C# can violate it silently.
3. **The registry approach is sound** — 17 patterns verified correct. The panels are real. The problem is assembly, not panels.
4. **Bluejohn** — looks like stone, crumbles when you touch it. The trial artifacts looked like programs. They compiled. They had CLIs. But the CLIs were hollow shells that printed messages instead of calling logic.
