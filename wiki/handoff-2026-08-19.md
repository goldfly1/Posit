## What Was Done

### 1. DafnyImplementationPhase Z3 Correction Loop (the main fix)
Same pattern as DafnyFixer: generate → Z3 reject → feed previous Dafny + Z3 errors back → fix → verify.
Max 3 attempts. The model sees its previous output AND the Z3 errors, so it can do a targeted fix
instead of rewriting from scratch.

**Proof it works** (from T6 trial log):
```
[dafny-impl] TempConverterLogic attempt 1/3: Z3 rejected:
  this symbol not expected in Dafny
[dafny-impl] TempConverterLogic Z3 verified + translated on attempt 2
[dafny-implementation] success (attempt 0)
```

Attempt 1: model output JSON (not Dafny). Z3 rejected with "this symbol not expected".
Attempt 2: correction loop fed error back with "⚠️ CRITICAL: Your previous output was NOT valid Dafny code!"
Model output proper Dafny. Z3 verified + translated. Success.

### 2. "Not Dafny" Error Detection
When Z3 says "this symbol not expected in Dafny", the correction prompt explicitly tells the model:
"Your previous output was NOT valid Dafny code! Output ONLY raw Dafny source code."
This catches the common failure where the model wraps Dafny in JSON instead of outputting raw code.

### 3. Pseudocode Crystallization Fix
The `IsCrystallized` check was trivially passing on pass0 (the raw spec) because pass0 contains
`method` and `returns` tokens in the signature line, which were being skipped. After skipping
sig/responsibility/test lines, zero substantive lines remained, and it returned `true` (vacuously).
Fix: require at least one substantive (non-filtered) line. If no substantive lines, it's NOT crystallized.

### 4. Broadened JSON Dafny Extraction
The JSON scanner was only looking for strings containing `"method "` or `"module "`. Now it also
detects Dafny code fragments containing `"var "`, `":="`, `"if "`, `"return "`, `"requires "`,
`"ensures "`, `"function "`, `"datatype "`.

The WireFixer is stuck cycling between `isValid`/`result` (lowercase) and `IsValid`/`Result` (PascalCase)
casing. The Dafny datatype uses lowercase field names (`isValid`, `result`) but C# convention is PascalCase.
The Dafny-to-C# translator generates `_IConversionResult` with specific property names, and Wire.cs
keeps guessing the wrong casing. 6 WireFixer retries all fail with the same error.

## Known Issues for Next Session

1. **WireFixer casing issue** — the Dafny datatype fields are lowercase (`isValid`, `result`) but
   C# properties are PascalCase (`IsValid`, `Result`). Wire.cs can't find the right property names.
   The WireFixer alternates between casings but never finds the right one. This suggests the
   WireFixer needs to see the actual translated C# type definitions (the `_IConversionResult` interface)
   to know the exact property names, not guess.

2. **Pseudocode reduction may need tuning** — it crystallizes at pass 1, which means only one
   reduction pass runs. Need to see the actual reduced pseudocode to evaluate if it's useful.

3. **Model uses deepseek-v4-flash:cloud** for Dafny implementation — a weaker/faster model.
   The correction loop helps it recover from errors, but a stronger model (deepseek-v4-pro:cloud)
   might produce correct Dafny on the first attempt. The architect uses flash for all phases
   currently (GetModelForPhase returns flash for all).
